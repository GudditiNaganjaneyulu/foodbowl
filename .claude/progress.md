## Real bugs found during verification (all fixed)

1. `apps/api/src/lib/tracing.ts` — used `resourceFromAttributes` which doesn't exist in the installed `@opentelemetry/resources` version; switched to `new Resource(...)`.
2. `apps/api/src/modules/menu/menu.routes.ts` — the update-menu-item schema included `modifierGroups`, which isn't a valid Prisma scalar update shape (it's a nested relation). Fixed by omitting `modifierGroups` from `updateMenuItemSchema` — nested modifier group edits need their own endpoint later, not silently accepted and ignored.
3. `apps/api/src/plugins/error-handler.ts` — `error` was typed `unknown` at the point `.message` was accessed; fixed by casting once to `Error & { statusCode?: number }`.
4. `apps/web/app/(admin)`, `(staff)`, `(delivery)` — used Next.js **route groups** (parentheses — no URL segment) where **real path segments** were needed. `(admin)/page.tsx`, `(staff)/page.tsx`, `(delivery)/page.tsx` were all silently colliding at `/`. Fixed by renaming to real folders: `app/admin/`, `app/staff/`, `app/delivery/`. `(public)`, `(customer)`, `(auth)` remain as genuine route groups since their children have distinct real path segments.
5. **Security**: `passwordHash` (the argon2 hash) was leaking in the `/api/v1/admin/users` list and create JSON responses — caught by actually curling the endpoint and inspecting the response, not by reading the code. Fixed with Prisma's `omit` API (`previewFeatures = ["omitApi"]` added to `schema.prisma`, regenerated client, applied `omit: { passwordHash: true }` to every `User` query in `admin-users.service.ts`).
6. ESLint peer-dependency conflict: root installs ESLint 9 (flat config, for api/shared), but `eslint-config-next@14.2` wants ESLint 8. Pinned `apps/web`'s own `eslint` devDependency to `^8.57.1` so pnpm resolves a compatible nested copy for that workspace.

## `docker compose up` — 3 real bugs found and fixed (2026-09-22)

The user ran the full stack and hit these, in order, as each fix uncovered the next:

1. **`web` container: `Cannot find module '.../next/dist/bin/next'`.** The named volumes (`web_node_modules`, `api_node_modules`) are mounted at a path *inside* an already bind-mounted parent directory (`../apps/web:/repo/apps/web`) — a well-known Docker gotcha where the volume doesn't reliably inherit the image's baked-in contents on first creation, so it's just empty at runtime even though the image built correctly. Fixed by changing both Dockerfiles' `dev` stage `CMD` to run `pnpm install --filter <pkg>...` (fast — the pnpm store from the `deps` build stage is already warm, no network fetch) before starting the dev server, so the volume gets populated at container start regardless of build-time state. Also regenerates the Prisma Client for the api container, since that output lives inside the same shadowed `node_modules`.
2. **`api` container: `ERR_UNKNOWN_FILE_EXTENSION` on `tracing.ts`.** The old approach bootstrapped OpenTelemetry via `tsx watch --import ./src/lib/tracing.ts src/server.ts`. `tsx watch` runs the app in a worker thread, and forwarding a `.ts` file through `--import` to that worker didn't reliably get tsx's TypeScript loader applied to it in this Node/Docker combination — even though the identical command worked fine run directly on the host earlier this session. Fixed by dropping `--import` entirely and instead making `import './lib/tracing'` the literal first line of `server.ts` — ES module import ordering guarantees its side effects (registering OTel's instrumentation hooks) run before `fastify`/`pg`/etc. are loaded, with no dependency on CLI flag propagation through worker threads. Simplified `dev`/`start` scripts in `apps/api/package.json` to match.
3. **`api` container, after the above two fixes: `PrismaClientInitializationError` — `libssl.so.1.1: cannot open shared object file`.** `node:20-slim` ships no OpenSSL at all, so Prisma's runtime libssl-version detection finds nothing and silently guesses wrong (defaults to `openssl-1.1.x`, which doesn't exist on this image either — Debian Bookworm ships OpenSSL 3.x). This only surfaces once something actually hits the database (health check, login, menu fetch), not at container start or build time, which is why it wasn't caught earlier. Fixed by adding `RUN apt-get update && apt-get install -y openssl && rm -rf /var/lib/apt/lists/*` to both the `base` and `prod` stages of `apps/api/Dockerfile` (they're separate `FROM` stages, both need it independently). Since Prisma Client now gets (re)generated fresh inside the container at startup (fix #1), it correctly auto-detects the container's actual platform once openssl is installed — no explicit `binaryTargets` config needed.

Added a root `.dockerignore` (`node_modules`, `.next`, `dist`, `.git`, `.env*`) alongside these fixes, mainly to stop the Dockerfiles' wholesale `COPY apps/web apps/web`-style commands from ever dragging host-built (macOS) artifacts into the build context.

**Verified, not just theorized**: rebuilt both images (`docker compose up -d --build api web`), confirmed 0 container restarts (`docker inspect --format RestartCount`), confirmed `web` serves 200, and confirmed `api`'s `/health/ready` and `/api/v1/menu` succeed against the live Neon DB from inside the running container — the actual failure path the user hit, now closed.

## Upstash Redis integration (2026-09-22)

User pasted a `REDIS_URL=rediss://...upstash.io:6379` into `.env` and asked to "use redis as well for it" with `import { Redis } from '@upstash/redis'`. Two things to know if picking this up again:

- **The `REDIS_URL` they added is the wrong credential type for `@upstash/redis`.** That package is Upstash's HTTP/REST client (works over `fetch`, no persistent TCP socket) — it needs `UPSTASH_REDIS_REST_URL` + `UPSTASH_REDIS_REST_TOKEN` from the Upstash console's **REST API** tab, not the `rediss://` TCP connection string from the **Connect** tab. These are genuinely different credentials, not just a formatting difference — flagged this clearly rather than guessing/faking a conversion. Pre-filled `UPSTASH_REDIS_REST_URL=https://powerful-mastiff-290638.upstash.io` in `.env` (same hostname, just https instead of rediss — that part's deterministic and safe to construct), but left `UPSTASH_REDIS_REST_TOKEN` blank rather than guessing it might equal the TCP password — it doesn't, and getting that wrong would just produce confusing 401s. **User still needs to paste the real REST token in.**
- **What it's used for**: the user didn't specify a use case ("for it" had no clear referent), so picked the two most natural, well-scoped, low-risk wins rather than asking a clarifying question (per this session's bias toward action): (1) fixed-window rate limiting (`lib/rate-limit.ts`, INCR+EXPIRE) on `/auth/login` (10/min/IP), `/auth/register` (10/hour/IP), `/users/me/password` (10/min/IP) — all three are credential-guessing targets; (2) cache-aside on `GET /api/v1/menu` (60s TTL) with explicit invalidation on every menu-write route (create category, create/update/delete item), not just TTL expiry.
- **Optional by design, not a hard dependency**: `lib/redis.ts` exports `redis: Redis | null` — null when the REST env vars aren't set, with a one-time boot warning (not silent). Every call site checks for null and no-ops (rate limiting: never blocks; caching: always falls through to Postgres) rather than crashing. **Verified live**: started the API with no Redis env vars set, confirmed the boot warning fires, and confirmed `/auth/login` and `/api/v1/menu` both still work normally (rate-limit/cache middleware correctly no-op, no errors).
- **Not verified**: the actual Redis-connected behavior (a real 429 after exceeding the rate limit, a real cache hit/miss cycle) — no real Upstash REST token was available to test against. This is a real gap, not something to assume works just because the no-Redis path was verified.
